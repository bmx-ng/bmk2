# nRF52840 feasibility audit (5 November 2026)

## Decision and evidence status

**Go for a staged Zephyr integration; physical Zephyr bring-up passed.** The SoC has enough resources for the existing compact runtime, and Zephyr describes a `promicro_nrf52840` board. The user's board is marked **“Tenstar Robot ProMicro NRF52840”** on its reverse and visually matches the image on the Zephyr page. Initially it enumerated as Adafruit “Feather nRF52840 Express” USB serial (VID:PID `239a:8029`, `/dev/cu.usbmodem101`). After the user's reset, its mounted `NICENANO` UF2 bootloader enumerated as Nice Keyboards `239a:00b3` and reported `Model: nice!nano`, `Board-ID: nRF52840-nicenano`, bootloader 0.6.0 (19 June 2021), and SoftDevice S140 6.1.1 in `INFO_UF2.TXT`. A stock Zephyr 4.5.0 hello-world image was built, flashed and observed over USB CDC. USB branding still does not prove the carrier revision. No debug probe was observed.

The [Zephyr board page](https://docs.zephyrproject.org/latest/boards/others/promicro_nrf52840/doc/index.html) explicitly calls this a *board type* covering nice!nano and clones, with no active maintainer. It lists `promicro_nrf52840/nrf52840` and `/uf2` targets, 256 KiB SRAM, 1 MiB flash, LED0 on P0.15, J-Link and pyOCD runners, and an Adafruit UF2 bootloader with double reset **for the documented board**. A [Tenstar Robot product manual mirror](https://manuals.plus/ae/1005007426478606) also describes a UF2 bootloader and USB-C programming, but does not prove this unit's installed firmware. The SoC has a 64 MHz Cortex-M4F, BLE/802.15.4 radio, USB device, QSPI peripheral, NFC-A, 12-bit ADC, PWM and 1 MiB/256 KiB memory per [Nordic](https://www.nordicsemi.com/Products/nRF52840). External QSPI flash, antenna design, regulator, battery charger, buttons, other LEDs and exposed signals are carrier choices. The [nice!nano v1/v2 drawings](https://nicekeyboards.com/docs/nice-nano/pinout-schematic/) are references, not proof that a clone matches them; v1 reserves P0.04 for battery sensing and uses P0.13 to gate VCC.

### Required board identity gate

Record USB VID/PID, product/serial strings, UF2 `INFO_UF2.TXT` contents and flash family ID if a mass-storage bootloader appears; inspect both normal and double-reset modes. Photograph both sides and inspect regulator, antenna, crystals, LEDs, buttons and SWD pads. If SWD is available, read FICR part/variant, UICR, flash/RAM information and existing flash layout **read-only**. Compare the board's schematic or vendor pinout with Zephyr DTS/overlay before selecting an image. Record USB power and GPIO voltage constraints. Probe bootloader only without a mass erase. The `nrf52840` SoC description should own CPU, memory, FPU and peripherals; `promicro_nrf52840` board profiles should own pin aliases, clock sources, USB/bootloader mode, LED polarity, flash reservations and runner policy. Preserve a separately named clone profile if the connected board differs.

The application-mode `239a:8029` USB interface exposes serial; the bootloader mode exposes a mounted UF2 disk and serial. The [Adafruit nRF52 bootloader documentation](https://github.com/adafruit/Adafruit_nRF52_Bootloader) describes entering UF2 by two resets within 500 ms. The Zephyr board page specifies briefly bridging **RST to GND twice** for Pro Micro style carriers, which need not have a reset button. The mounted `CURRENT.UF2` was inspected read-only: 2,752 UF2 blocks, addresses `0x1000` through `0xAD000`, family ID `0x239a00b3`. This snapshot spans more than the application and does **not** itself establish the safe application start/end. A 1200-baud serial touch is another possible entry path in the Adafruit ecosystem, but may select serial-only DFU; do not infer a UF2 drive from that method.

### Physical bring-up result

A temporary Zephyr 4.5.0 workspace and ARM Zephyr SDK 1.0.1 were installed under `/private/tmp/nrf52-zephyr`, with a Python 3.13 venv. The stock `samples/hello_world` built for `promicro_nrf52840/nrf52840/uf2`; its generated UF2 carried family `0xada52840` and addresses `0x26000`–`0x31000`, wholly inside the [Zephyr S140 v6 application partition](https://github.com/zephyrproject-rtos/zephyr/blob/main/dts/vendor/nordic/nrf52840_partition_uf2_sdv6.dtsi) (`0x26000`–`0xEC000`). The linker reported 44,892 B flash and 14,776 B RAM used. Before flashing, `CURRENT.UF2` was copied read-only to `/private/tmp/nrf52-zephyr/current-before-flash.uf2` (SHA-256 `6a2f0d485a72b3ce23b419e3ed81625ba36b8a6b42f2f9bb25bf5e3e0f1ed54b`). `west flash -r uf2 --board-id nRF52840-nicenano` succeeded. The board then appeared as USB CDC VID:PID `2fe3:0004` and emitted `*** Booting Zephyr OS build v4.5.0 ***` and `Hello World! promicro_nr...` (the captured output ended mid-line). This verifies build, UF2 upload, reset and a working console. It does not yet test managed BlitzMax, repeated upload or a full console line.

## Platform choice

| Route | Assessment |
| --- | --- |
| **Upstream Zephyr application containing generated BlitzMax C** | **Recommended first route.** The public board target and J-Link/pyOCD/UF2 paths exist; Zephyr owns startup, linker, drivers, USB and BLE. Keep the BlitzMax adapter as ordinary Zephyr application C plus a small board overlay. Pin a known Zephyr release/commit. |
| nRF Connect SDK/Zephyr | Viable later, especially for Nordic-specific radio features and production support. NCS is Zephyr plus Nordic components, including some proprietary software [per Nordic](https://www.nordicsemi.com/Products/Development-software/nRF-Connect-SDK). It is not required for a Zephyr hello-world or basic BLE. Test the same adapter against a pinned NCS version after upstream bring-up. |
| nrfx/bare metal | Could minimize kernel cost, but would require new startup/linker, console, USB, BLE integration, event dispatch and flash support; it loses substantial reuse. Nordic's current NCS bare-metal offering is described for nRF54L, not this nRF52 target. |

Zephyr [supports Ubuntu, Apple Silicon macOS and native Windows](https://docs.zephyrproject.org/latest/develop/getting_started/); its current guide requires CMake 3.28, Python 3.12 and devicetree compiler 1.4.6. Use a Python venv for `west` and manifest requirements, CMake/Ninja and the [Zephyr SDK ARM toolchain](https://docs.zephyrproject.org/latest/develop/toolchains/zephyr_sdk.html). Windows WSL needs USB forwarding for flashing. Select a pinned stable Zephyr release and record `west manifest --freeze`, toolchain version and board revision. Configure `zephyr.base`, `zephyr.west`, `zephyr.sdk` and optional runner/serial paths in `custom.bmk`; discover `ZEPHYR_BASE`, a `west` workspace, registered Zephyr CMake package and installed Zephyr SDK with explicit paths taking precedence. Fail with a precise missing-tool message. No SDK code needs vendoring; audit licenses of any optional Nordic binary before distribution.

### Flashing and console

The documented UF2 variant compiles with `-b promicro_nrf52840/nrf52840/uf2`; the page says double reset then `west flash`. Generic board docs list J-Link/pyOCD as runners. Neither MCUboot nor a J-Link interface is proven to be on this carrier. `nrfutil`/Nordic tools require a matching transport and image format and are not a default. `-x` should build and flash through the verified board profile, then restart and follow the selected USB CDC or UART console with a bounded wait and an identity check. Never automatically use SWD mass erase or overwrite UICR/bootloader. A serial port may disappear and re-enumerate on reset; match USB identity, not a stale `/dev` path.

Proposed UX: `bmk makeapp -l nrf52 -g arm -board promicro_nrf52840 hello.bmx`; `bmk makeapp -x -l nrf52 -board promicro_nrf52840 hello.bmx`; `bmk boardinfo -l nrf52 -board ...` for board-derived capabilities and reservations; `bmk deviceinfo -l nrf52` for detected USB/UF2/SWD facts, explicitly marking unknown fields. Board selection may infer `nrf52/arm`; mismatched explicit target or arch must fail. The profile should declare a `uf2` or `swd` programming variant only after device inspection.

## Compiler, runtime and repository integration

The target is 32-bit little-endian ARMv7E-M Thumb-2, Cortex-M4F. Zephyr must choose the final ABI and flags consistently for all generated C and native libraries (`-mcpu=cortex-m4 -mthumb`, with its configured `-mfpu=fpv4-sp-d16` and `-mfloat-abi=hard` if hardware FP is enabled). A soft/softfp build is possible only when **every** object and library agrees; do not mix calling conventions. Zephyr CMake should supply the actual compile/link flags rather than duplicating them in bmk. Check stack alignment (AAPCS 8-byte public boundary), descending stack, `setjmp`/`longjmp`, and compiler generated exception frames with the chosen libc/toolchain.

Compiler source currently validates only Pico/ARM and ESP32/Xtensa or RISC-V in `BlitzMax-bcc2/mod/blitzmax.mod/compiler.mod/compiler_options.bmx` (lines 123-145). Its default symbols (line 166 onward) and embedded predicate must gain `nrf52`, `nrf52arm`, `embedded`, `arm`, `ptr32`, `longint4`, `littleendian`; `?pico` must stay false. `bcc2/tests/test_compiler_ir.bmx` lines 313-327 is the existing target matrix to extend. Audit C emission for Pico-only includes, startup symbols and native ABI before calling the lowering reusable. The maintained compiler module source needs to be located in its owning source repository; the copies under `BlitzMax-bcc2` and `BlitzMax-pico` are SDK distributions and are not Git checkouts.

`bmk_src/bmk_embedded_board.bmx` resolves only Pico/ESP32 boards; `bmk_src/bmk.bmx` lines 328-335 and 442-455 dispatch and validate only those targets. `bmk_src/bmk_deviceinfo.bmx` line 126 limits `boardinfo` to ESP32. `bmk_src/bmk_config.bmx` contains the existing CLI options/help. Add `bmk_nrf52.bmx`, a small board-profile parser/registry, target dispatch and Zephyr application generation analogous to `bmk_esp32.bmx`, but with Zephyr CMake owning build settings. Generate in `.bmx`, matching existing ignored build output. Avoid reusing the Pico-named heap and float options in the new user interface; introduce target-neutral `-heap` only as a deliberate compatible migration.

The shared compact runtime in `BlitzMax-pico/mod/embedded.mod/runtime.mod/native/embedded_runtime.c` has a 16-byte aligned static arena by default (lines 6-76), one execution context by default (lines 23-37), precise roots, automatic collection/retry and static allocation-failure exceptions. Its [integration contract](../../BlitzMax-pico/mod/embedded.mod/docs/runtime-integration.md) describes managed owner context and deferred native events. The Pico adapter's `embedded_platform.h` checks core/exception state and uses Pico panic APIs; the nRF adapter must instead reject Zephyr ISR and foreign threads, own a fixed main-thread identity, panic via bounded console output, and expose a static arena in RAM. Start in Zephyr's main thread with a configured stack, rather than allocating a dedicated managed thread. USB/BLE/timer callbacks enqueue bounded native records; `PollSystem`/`WaitSystem` drain on the owner thread. Register another managed thread only after GC synchronization is designed and tested; single-core nRF52840 does not need the unfinished multicore mode. `BRL.StandardIO` currently selects only Pico or ESP32 in `BlitzMax-pico/mod/brl.mod/standardio.mod/standardio.bmx`; add an nRF52 binding to a Zephyr console adapter. Verify the appstub, type initialization, globals, object/array/string allocation, exceptions and shutdown path on device.

**Memory budget is a planning estimate, not a measured build:** 256 KiB total SRAM. Reserve 64 KiB static managed arena initially, 16 KiB managed main stack, roughly 40-80 KiB for Zephyr, USB console, native queues/stacks and C data, leaving about 96-136 KiB uncommitted before BLE. Recompute from Zephyr map/`ram_report` after each feature. With BLE host/controller, security and connection buffers, expect tens of KiB more and reduce the managed arena to 32-64 KiB as measured. Flash has 1 MiB physically, but the executable area depends on the verified bootloader/MCUboot partition; establish it from DTS and device before setting a limit. Report arena capacity/used/high-water, Zephyr heap use, thread stack high-water and flash/RAM section sizes. Prefer static allocation and set Zephyr heap separately; native allocations must not silently consume managed arena. Initial 64 KiB/16 KiB values are hypotheses to validate against the real image and stack usage.

### Module ownership

Keep `Embedded.*` contracts and shared runtime in `embedded.mod`; add `nrf52.mod/runtime.mod` and `nrf52.mod/io.mod` adapters plus board profiles and Zephyr CMake templates in a new target repository following `esp32.mod` conventions. Reuse BRL embedded modules where source semantics match. Put FICR/UICR, radio-specific controls and other nonportable features under `NRF52.*`; do not turn those into `Embedded.*` aliases. Use the target repo's `.gitignore` for generated `.bmx`, CMake, ELF/HEX/UF2 and module artifacts. Keep changes on task branches across owning repositories, with coherent local commits; no push is authorized.

## Milestones and gates

1. **Hardware/SDK gate (partly passed):** USB/UF2 identity, S140 v6 flash partition, stock Zephyr build/upload and USB console are verified. Exact carrier revision, full pin map and SWD access remain unverified.
2. **Compiler/build gate:** accept `nrf52/arm` and symbols; add board inference and Zephyr app generation; compile generated C with the pinned Zephyr SDK. Reject mismatched ABI and missing toolchain.
3. **Managed vertical slice:** Zephyr main enters BlitzMax, prints through `BRL.StandardIO`, allocates objects/arrays/strings in a bounded arena, reports deterministic OOM, handles exceptions, survives repeated reset/upload. Then enable `-x`, `boardinfo`, `deviceinfo` with verified identity checks.
4. **Portable peripherals:** monotonic time/alarms, GPIO/events, RNG, UART/buffered UART, I2C/SPI, ADC/PWM, watchdog/reset/device ID; use shared conformance programs under `embedded.mod/tests`, with pin loopbacks and native callback queue tests. Add storage only after reserving a flash partition and measuring erase wear; USB device beyond console after descriptor/endpoint review.
5. **Radio/power:** Zephyr provides a same-chip BLE host/controller architecture ([Zephyr Bluetooth architecture](https://docs.zephyrproject.org/latest/connectivity/bluetooth/bluetooth-arch.html)). Map the shared BLE surface to Zephyr advertising, scanning, GATT, connection and security APIs; measure RAM/flash and keep callbacks native. Test peripheral and central roles, GATT client/server, bonding and reconnection with a second device. IEEE 802.15.4, Thread, Matter, Zigbee and NFC are later nRF-specific work. There is no native Wi-Fi; ordinary IP sockets require a configured transport. Add sleep/wake only after defining managed heap retention and wake sources.

Host tests should cover target/symbol validation, board profile parsing, generated CMake and command construction; shared compiler/runtime tests cover roots, type creation, dispatch, arrays, strings, exceptions, GC stress and deterministic OOM. Device tests should verify identity before flashing, then hello/reset/upload, USB console stability, stack and binary-size margins and the peripheral loopbacks above. Maintain repeatable logs with Zephyr commit, toolchain, board USB identity, build variant and memory map. **Go/no-go:** fail the effort if the physical board cannot be identified safely, the generated C cannot link with the Zephyr ABI, or the minimal application cannot retain a useful managed arena (initial acceptance: at least 32 KiB) with safe stack margin. No physical target claim before those gates pass.

## Implementation progress (5 November 2026)

The compiler module now accepts `nrf52/arm` and emits the embedded, ARM, 32-bit, little-endian and nRF52 symbols. The existing compiler IR test passed after rebuilding the SDK compiler. `bmk` now selects `promicro_nrf52840`, generates the existing embedded C build bundles and builds a Zephyr application. The Zephyr template links the shared compact runtime and a new adapter that binds its single managed context to the Zephyr main thread, rejects ISR/foreign-thread entry, and implements `BRL.StandardIO` through the console. The user-facing build command and environment are in `nrf52.mod/README.md`.

The first managed `nrf52_hello.bmx` built successfully for Zephyr 4.5.0 and SDK 1.0.1. Zephyr reported 73,304 B flash and 96,376 B RAM, with a 64 KiB managed arena and 16 KiB main stack configured. Its UF2 starts at `0x26000` and is 146,944 B. The source and artifacts are local; subsequent physical uploads verified the managed USB greeting and the `-x` path. `-x` assumes the identified `NICENANO` bootloader is mounted. Automatic bootloader entry and peripherals remain open milestones.

The first managed UF2 was flashed on the connected `NICENANO` drive after rechecking `INFO_UF2.TXT` for `Board-ID: nRF52840-nicenano` and S140 6.1.1. Zephyr restarted as USB CDC `2fe3:0004`; the serial capture showed repeated `Hello from BlitzMax on nRF52840` lines. The first line was truncated while the serial reader attached, but subsequent complete lines establish that the managed main loop and standard output work. The image SHA-256 was `9763e309b01bb1c956db92e7e8b97b6d0089a26f4b9e1cc3fb1137a7a8eb4dbc`. The sample was subsequently expanded with object, array, exception and time checks; the final device result is recorded below.

The expanded sample built and uploaded using `bmk makeapp -r -x -l nrf52 -g arm -board promicro_nrf52840`. Its image used 74,132 B flash and 96,376 B RAM; the UF2 remained inside `0x26000`–`0xEC000`. On serial attach, the device emitted the start of the success-only line `NRF52_MANAGED,objects=pa...`, then repeated complete managed greeting lines. The success branch requires object field arithmetic, array indexing and a caught string exception to all pass. Serial attach truncated the one-time line, so a complete status line was not captured. The `bmk -x` build-and-upload path and repeated managed output are physically verified.

The Zephyr CDC ACM driver was observed dropping bytes when consecutive `Print` calls filled its transmit FIFO. The application overlay now enables CDC ACM transmit flow control and a 2 KiB FIFO. After rebuilding and flashing, a five-second USB CDC capture contained six complete cycles of `NRF52_MANAGED,objects=pass,arrays=pass,exceptions=pass,time=pass` followed by `Hello from BlitzMax on nRF52840`. The timing check requires a 25 ms `SleepMilliseconds` to advance `MonotonicMilliseconds` by at least 25 ms. Zephyr reported 74,264 B flash and 97,976 B RAM (37.37%) for that image. The portable time adapter is thus device verified. `BRL.StandardIO` writes CRLF and Zephyr's console inserts an additional CR, so the captured line endings are `\r\r\n`; terminals still display separate lines. Full peripheral and BLE APIs remain future milestones. Upstream Zephyr and the Zephyr SDK are sufficient for this bring-up; Nordic Connect SDK is optional for later Nordic-specific integration.

## Namespace and ownership update

The target adapter and Zephyr template now live in a dedicated top-level `nrf52.mod` source repository and SDK module root. Its public modules are `NRF52.Runtime`, `NRF52.System.Time`, `NRF52.System.Device` and `NRF52.IO.StandardIO`, matching the `Pico.*` and `ESP32.*` naming pattern. Shared code and portable contracts remain under `Embedded.*`; `BRL.StandardIO` continues to select the target adapter automatically. The `bmk` template path is `mod/nrf52.mod/cmake/application`. A namespace-importing example built successfully with Zephyr 4.5.0: 74,328 B flash and 98,040 B RAM. The later device diagnostic built from this moved layout and passed on device.

## Device identity and reset-cause result

`bmk deviceinfo -l nrf52` now distinguishes the normal Zephyr USB serial interface (`2fe3:0004`) from the nice!nano UF2 bootloader (`239a:00b3`). In bootloader mode it reads `INFO_UF2.TXT` and reported `Board-ID: nRF52840-nicenano`, `Model: nice!nano`, and `SoftDevice: S140 version 6.1.1` on the connected board. It deliberately does not claim to know the SoC ID or reset cause from generic USB descriptors.

`NRF52.System.Device` now exposes Zephyr's eight-byte SoC device ID, reset-cause flags, and supported reset-cause mask. The portable device adapter maps a reset cause to `Embedded.System.Device` and provides cold reboot. The `nrf52_device.bmx` diagnostic built to a 74,304 B flash / 97,976 B RAM image. After UF2 upload, the board repeatedly printed `NRF52_DEVICE,id=pass,reset_api=pass,cause=1` over USB serial. The test verified a 16-character hexadecimal ID, eight ID bytes, a stable reread, and a nonzero supported-cause mask; it did not publish the unique ID. The raw cause value `1` is Zephyr's pin-reset flag, consistent with the physical reset used to enter UF2. Reboot is implemented but not yet exercised on the board.

## Managed arena stress result

The `nrf52_memory.bmx` diagnostic fills most of the 64 KiB managed arena with rooted 1 KiB objects, releases alternating roots, collects, then verifies that a new object occupies one of the freed gaps without advancing the arena high-water mark. It checks heap integrity, catches an allocation failure for an object too large for the arena, releases the remaining roots, collects, and allocates again. The final build used 75,044 B flash and 97,976 B RAM. After UF2 upload, the board repeatedly printed `NRF52_MEMORY,fragmentation=pass,oom=pass,recovery=pass` over USB serial. This verifies the bounded arena's basic fragmentation reuse, deterministic OOM exception, and post-collection recovery on the physical board. It is a single-thread test; callback or radio allocation pressure remains untested.

## Random source and basic GPIO result

`Embedded.Random` now uses Zephyr's `sys_csrand_get()` and the enabled nRF hardware entropy driver with bias correction. Scalar requests stop on source failure; buffer fills return failure. The `Random.Core` dependency exposed a missing standard `MilliSecs` lowering hook, so the nRF runtime now implements that and the standard delay hooks. The image used 82,004 B flash and 98,168 B RAM. On the board, repeated `NRF52_RANDOM,source=pass,fill=pass,validation=pass` lines verified variation across scalar samples, a nonzero 31-byte fill, and invalid-argument handling. This is an integration check, not a statistical or cryptographic certification of the entropy source.

The first `Embedded.Hardware.GPIO` adapter supports input, output, raw level reads, output state and pull-up/down configuration through Zephyr GPIO devices. It numbers P0.00–P0.31 as 0–31 and P1.00–P1.15 as 32–47, rejecting the nRESET pin and USB data pins. Its example uses the board profile's P0.15 LED pin; the image used 76,164 B flash and 98,296 B RAM. On the connected board, repeated `NRF52_GPIO,output=pass,input=pass,pulls=pass,reserved=pass` lines verified configuration, output level readback and reserved-pin rejection. No external electrical loopback was measured, and the Tenstar clone's complete pin map is still unverified. Drive selection and board pin ownership remain for later work.

## GPIO events, ADC and PWM result

The nRF52 adapter now has a fixed 32-record native event queue and Zephyr semaphore wakeup. GPIO callbacks capture a numeric event and timestamp in interrupt context; `Embedded.Hardware.GPIOEvents` dispatches the managed event during `PollSystem`. The shared GPIO event wrapper needed explicit unsigned conversions for its close path under the strict nRF compiler; that source was corrected in `embedded.mod`. On the board, the P0.15 self-toggle example repeatedly printed `NRF52_GPIO_IRQ,rise=pass,fall=pass,managed=pass`, confirming both edge types and managed delivery with no queue drops. The image used 88,220 B flash and 100,536 B RAM. High/low level interrupt configuration is implemented but not yet exercised electrically; external pin input and bounce behavior remain untested.

`Embedded.Hardware.ADC` maps the eight nRF SAADC inputs to their P0 pins and exposes 12-bit raw readings. A P0.02 test image used 80,920 B flash and 98,296 B RAM. The connected board repeatedly printed `NRF52_ADC,setup=pass,read=pass,bounds=pass` after 16 reads, invalid-pin rejection and close-state checks. P0.02 was not tied to a reference voltage, so this verifies driver operation and range, not accuracy or calibration.

`Embedded.Hardware.PWM` initially supports the board profile's PWM0 output on P0.15. The diagnostic exercised frequency, duty, polarity, enable/disable and deinit through Zephyr; its image used 83,984 B flash and 98,360 B RAM. The board repeatedly printed `NRF52_PWM,frequency=pass,duty=pass,polarity=pass`. A USB status result confirms driver calls and state tracking; the electrical waveform has not been measured. Pin ownership between GPIO, PWM and ADC remains an explicit constraint.

## SPI loopback result

`Embedded.Hardware.SPI` now maps portable controller 0 to the board's SPI2 device, with fixed pins SCK P1.01, MOSI P1.02 and MISO P1.07. The Nordic peripheral supports 8-bit hardware transfers; the portable 16-bit calls use pairs of host-order bytes, matching the shared API's ESP32 implementation. Baud rates round down to one of the hardware's 125 kHz–8 MHz rates. The user connected the lower-right reverse-side pads marked 102 and 107 for a physical MOSI–MISO loopback. The image used 88,464 B flash and 98,552 B RAM. After UF2 upload, the board repeatedly printed `NRF52_SPI,loopback=pass,8bit=pass,16bit=pass,mode3=pass` over USB CDC. This verifies data transfer at 1 MHz in mode 0, read with repeated `$a5` at 500 kHz in mode 3 and LSB-first order, and 16-bit API data in mode 0. The test did not exercise chip select or an external SPI peripheral.

## UART loopback result

`Embedded.Hardware.UART` now maps portable controller 0 to the board's UART0, with fixed TX P0.09 (D10) and RX P0.10 (D16). The USB CDC console remains separate, so `UARTDefaultController` reports unavailable. The adapter provides polling 8N1 transfers, timed reads, runtime baud and format changes within the nRF UARTE's supported modes, receive error flags and optional CRLF translation. Hardware flow control, odd parity, TX break and buffered asynchronous operation remain unavailable. The user connected adjacent outer D10 and D16 pads. The 87,964 B flash / 98,488 B RAM image repeatedly printed `NRF52_UART,loopback=pass,8n1=pass` after a physical eight-byte loopback with a 100 ms read timeout for each byte. Continuous high-rate reception remains unverified; Zephyr's polling UARTE receives one byte at a time, so buffering is a later step.

## I²C controller result

`Embedded.Hardware.I2C` now maps portable controller 0 to Zephyr I²C1 because I²C0 shares hardware instance 0 with the working UART0. The board profile fixes SDA to P1.04 (D8) and SCL to P1.06 (D9), enables internal pull-ups, and supports 100 and 400 kHz. The adapter implements blocking writes, reads, and combined writes/reads with repeated Start. Zephyr's nRF driver has a fixed 20 ms timeout per message, so the timeout API rejects shorter requests rather than promising a deadline it cannot enforce.

The user connected the nRF D8 to the ESP32-S31 Function CoreBoard-1 pin printed `0` (GPIO0), D9 to the ESP pin printed `1` (GPIO1), and ground to a pin printed `G`. Both boards were powered independently by USB. A temporary ESP-IDF 6.1 I²C slave at address `0x42` returned `NRF!`; its source is retained under `nrf52.mod/tests/targets/esp32_s31_i2c_target`. The nRF Zephyr image used 91,868 B flash and 98,616 B RAM. After UF2 upload, USB CDC repeatedly printed `NRF52_I2C,write=pass,read=pass,restart=pass`, confirming a two-byte write, four-byte read, and combined write/read on the physical bus. The ESP test image was written only over its active OTA app partition after that partition was backed up. All eight 512 KiB chunks of the original app were restored and verified by the flashing tool; the ESP then booted its original `gc_stress_s31_psram` app and printed progress. The test does not yet cover 400 kHz, multiple slaves, long bus wiring, clock stretching, or error recovery.
